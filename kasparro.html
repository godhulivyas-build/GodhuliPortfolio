Kasparro · Auditing an AI-Visibility Audit

Don't ship the audit. Audit the audit.

A client report claimed Orivane won 87% of AI-search mentions. Before it went out, I checked the underlying workbook against its own execution logs and found 20 confirmed errors, three of which quietly inflated the client's best result. Then I specced the tool that catches this automatically next time.

01 · The Verdict

Fix part of it. Don't send it. Don't redo it all.

Four problems need brand-new tests — they can't be fixed by editing a spreadsheet. The other sixteen just need correcting on existing data.

20 / 20Confirmed errors, out of everything checked
4Need a full re-run, not a data fix
16Fixable by correcting the existing record

Two tests were logged as "answered from memory only," but the system's own execution data shows it actually looked things up online and attached sources. The log contradicts itself. One test has the opposite problem: logged as having searched, with zero sources actually attached. One question was never run on the target model at all, and one "test" was an accidental duplicate of another.

02 · Most Material Problems

Three errors that change what "winning" means.

The math errors are serious too, but these three are worse — they make specific quoted results unusable in front of a client.

1

The one clean #1 result may not be real

The audit's only clear #1 ranking, in a search where nobody named the brand, comes from a run whose own log contradicts itself about how the answer was produced. Until it's re-run, it can't be shown to a client as proof.

2

Five "proof" links don't actually back the claim

Five citations tagged as directly supporting a claim say otherwise on inspection. Worst case: one claims proof that a product "removes all wildfire smoke," but the same source admits it has no real testing behind it.

3

Two mislabelled tests inflated the win count

Two prompts that named the brand directly were coded as if it hadn't been mentioned — inflating the reported "non-branded win" count by three results that shouldn't have counted that way.

04 · Corrected Client Intelligence

What we know, think, guess, and don't know.

Four confidence levels, kept visibly separate, rather than one number presented as fact.

Know for sure

The brand was mentioned in 25 of 27 valid tests (93%), not the 26 of 30 (87%) first reported — that number wrongly included 2 broken tests and 1 duplicate. Two website claims don't match the brand's own verified specs.

The data suggests

When nobody says the brand name out loud, presence is inconsistent, not strong: missing in some runs, ranked fourth in others, appearing at varying ranks elsewhere. The one #1 result is the one that can't yet be trusted.

Best guess (not proven)

The contradiction on the #1 result might just be a logging glitch, not the system secretly searching when it wasn't meant to — can't confirm without a genuine re-run with full log visibility.

Still don't know

How the brand compares to competitors (no verified facts on file for any). What a real re-run of the broken tests would show. This audit says nothing about search rankings, traffic, or revenue.

05 · Prioritised Next Actions

Three places to fix, three different risks.

Audit platform

  • Re-run the three broken tests to settle whether the best result is real, and fill the coverage gap.
  • Fix every mislabelled test and source, then recalculate every reported number so it traces back to real data.

Client website

  • Fix or remove the two claims that directly contradict the brand's own verified specs.
  • Review the claims linking the product to health outcomes — the biggest reputational risk if wrong.

Independent authority

  • Decide whether to pursue the certification the website already implies.
  • Take a fresh copy of the live website before the next audit, to confirm these errors are still present.

06 · Product Decision

Build one tool. Leave two things unresolved.

An automatic check that catches these kinds of contradictions before a report is ever published — five parts, nine checks, the miscounted-numbers fix ships first.

5 partsCovering nine distinct checks
9–12 wkTotal build time estimate
20 / 20Design goal: every known error type caught

Not building yet: automatic health-claim scanning, live website checking, or any tool that fixes data on its own without a human. This is a design goal, not a proven track record — it hasn't been measured on a brand-new audit yet.

07 · The Consistency Gate (PRD)

Five checks, before Preliminary can become Approved.

Audit exports can currently reach "Preliminary" with duplicate runs, provenance contradictions, incorrect labels, broken citations and wrong summary metrics — caught manually today, one row at a time. The gate validates every export automatically before it can move from Preliminary → Reconciled → Approved, while a person stays responsible for every correction.

Approval requires zero unresolved Blockers and zero unresolved Reviews; Warnings may remain.

SeverityMeaningRelease impact
BLOCKERDeterministic contradictionStops Approved until fixed or overridden
REVIEWAI-assisted, likely contradictionRequires a recorded human decision
WARNINGPartial or unclear evidenceShown to analyst; does not block
PASSEDDeterministic check is cleanContinue

AI-assisted checks never display "Passed" — a clean judgment-call check remains not flagged, not verified. Blocker overrides require PM sign-off, a mandatory reason and timestamp, with an append-only audit trail. The tool never changes labels, numbers or text itself; it flags, a human fixes the source, and the gate re-runs.

Deterministic + AI-assisted checks Append-only audit trail Human stays the fixer

V1 scope. Includes workbook consistency, execution provenance, evidence/citation validation and summary metrics. Excludes live website checking and health-outcome claim scanning — both listed explicitly as "not building yet."
